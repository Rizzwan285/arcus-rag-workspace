# Retrieval Evaluation

A benchmark for the three retrieval configurations Arcus can run: the dense
(pgvector/HNSW) arm alone, the lexical (tsvector/GIN) arm alone, and Reciprocal
Rank Fusion over both.

Latest numbers: **[RESULTS.md](RESULTS.md)** (regenerated by `npm run eval`).

## Running it

```bash
npm run eval            # seed → measure → tear down → write RESULTS.md
npm run eval -- --keep  # leave the fixture in the database for inspection
npm test                # unit tests for the metrics, query builder, and dataset
```

Requires `DIRECT_URL` (or `DATABASE_URL`) and `GOOGLE_API_KEY`. Embeddings are
cached in `eval/.cache/` after the first run, so subsequent runs make no API
calls and produce byte-identical vectors.

## What it measures

| Metric | Definition |
| :--- | :--- |
| **Recall@k** | Fraction of a query's relevant passages inside the top k. Capped by `k / |relevant|` — a query with 2 relevant passages has a Recall@1 ceiling of 0.5. |
| **Hit@k** | 1 if *any* relevant passage is in the top k. Equals Recall@k when a query has exactly one relevant passage. |
| **MRR** | Mean of `1 / rank` of the **first** relevant passage. |
| **nDCG@10** | The only metric here sensitive to ordering *within* the top k. |

All are macro-averaged: every query counts equally regardless of how many
relevant passages it has.

## Design

**The three systems share one SQL statement.** `HYBRID_SEARCH_SQL` gates each arm
behind a boolean parameter (`$11`, `$12`), so "vector only" is the production
query with the lexical CTE emptied — not a separate implementation. Any measured
difference is attributable to fusion rather than to incidental differences in how
three retrievers were written.

**Fixture corpus, not production data.** The production corpus is a single PDF
whose text layer is partly mangled by a custom font encoding, which makes it
useless as ground truth. `dataset/corpus.ts` holds 103 passages across four
synthetic course documents, written so that each subject contains several
confusable near-neighbours.

**Isolated and self-cleaning.** The fixture is seeded under a fixed user id that
no OAuth account can map to, and removed in a `finally` block. Teardown deletes
one `User` row and relies on the schema's cascades, so it cannot touch anything
it did not create. A crashed run is cleaned up by the next one.

**Nothing is tuned to the results.** `k = 60`, the candidate pool, and the arm
weights are all at their shipped defaults.

## Query set

30 hand-labelled queries, assigned to a category **before** any retrieval was
run, so a failed prediction stays visible in the per-category breakdown:

| Category | n | Phrasing | Expected winner |
| :--- | ---: | :--- | :--- |
| `paraphrase` | 10 | Conceptual, little vocabulary overlap with the passage | Dense arm |
| `exact-term` | 10 | Course codes, named theorems, acronyms | Lexical arm |
| `mixed` | 10 | Natural question carrying a distinctive term | Fusion |

## Significance

With 30 queries, a few points of difference is noise. Every comparison is
reported with a **paired bootstrap** 95% confidence interval (10,000 resamples,
fixed seed). Paired because both systems answer the same queries, which removes
query difficulty as a source of variance. An interval straddling zero is
reported as *not significant* rather than as a win.

## Threats to validity

Stated in full at the bottom of [RESULTS.md](RESULTS.md). The short version:
the corpus, the queries, and the relevance judgements share an author; the
corpus is synthetic and small; and at 103 rows this measures **ranking quality,
not ANN index recall** — the planner may not choose the HNSW index at that size.
Index usage on the real corpus is verified separately by `npm run db:verify`
and `EXPLAIN ANALYZE`.
